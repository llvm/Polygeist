# lib_v3 — specifications from OpenBLAS source

lib_v3 is a second, independent spec suite. lib_v2 takes library semantics from
the netlib reference BLAS/LAPACK; lib_v3 takes them from the source of a real
optimised library, OpenBLAS 0.3.31 (BSD-3-Clause), using its portable C code
path: the CBLAS interface logic plus the plain-C kernels (`kernel/arm/*.c`,
`kernel/generic/*.c`). The architecture-specific assembly kernels and the
blocked level-3 drivers are not usable as specifications and are not used.

The cited source files are kept with checksums in
`~/netlib_ref/openblas-0.3.31/` (`SHA256SUMS`).

```
ref_c/<routine>.c        C transliteration (cites file + line ranges)
manifest/<routine>.json  specialisations, target CBLAS call, assumptions
raised/                  generated by build_lib_v2.py
RAISE_STATUS.md          generated
import_manifest.json     generated input, compiler, and MLIR hashes
../kernel_library_v3.mlir  generated: one kernel.defn per RAISED spec
```

Build and use (the same scripts as lib_v2, selected by an environment variable):

```
POLYGEIST_SPEC_SUITE=lib_v3 /usr/bin/python3 scripts/correctness/lib_v2/build_lib_v2.py -j 2
/usr/bin/python3 scripts/correctness/spec_match.py IN.mlir -o OUT.mlir --backend cpu --report match.json
```

`polygeist_build.sh` and `kernel_match_rewrite.py` now use `spec_match.py`.
Recognition uses only bodies imported from reference code, through the Linalg
dataflow matcher and the generic region matcher. The old Python composition
formulas, named operation predicates, and handwritten structured rewrites have
been removed. ABI-only definitions in `kernel_library_phase2.mlir` cannot
authorize a production replacement.

The application and reference import share `lib_v2/recipe.py`, including
delinearization and `--no-inline`. Preserving the selected function until
replacement prevents a whole-program build from optimizing a dead copy while
executing an earlier inlined copy. The final compiler may inline the replaced
function. Optional raising stages retain their legal input if a compiler pass
fails, recording the failed command and diagnostic. If an unmatched function's
tensor views cannot be lowered, the builder retains its original affine IR and
records zero replacements. It never uses this recovery to excuse an invalid
library call. Runtime tracing (`POLYGEIST_V2_TRACE=1`) confirms which vendor calls
actually execute.

The default `POLYGEIST_NUMERIC_MODEL=strict` preserves scalar operation trees
and refuses references with documented deviations. `relaxed` explicitly allows
real-arithmetic identities, reassociation, and reduction summaries. It assumes
finite arithmetic without exceptional intermediate results, treats signed zero
as insignificant, and is not a bitwise IEEE-754 equivalence guarantee. Numerical
validation against the original application and actual vendor backend is still
required. Strict refers to the scalar matching policy; it does not promise
bitwise agreement with a vendor library's internal reduction order. Both
models retain numeric cast operations and their types; an error
budget alone does not justify a match.

The match report records reference/manifests, generated-library hashes, matcher
sources, numeric model, backend, selected APIs, and operand bindings. The build
checks it before ABI lowering. Resuming with `--semantic-mlir` requires
`POLYGEIST_MATCH_PROOF` for that exact IR and configuration. Rebuild the library
after changing reference inputs, the import recipe, or compiler binaries;
`--no-raise` and `--no-validate` do not produce an import attestation.

Import validation is recorded separately for the Affine, memref-Linalg, and
debufferized stages. The generic matcher uses only a stage that passed its
reference-output check. For example, a failed tensor-stage check does not
validate that tensor IR and does not invalidate an independently checked
Affine stage. Failed tensor definitions remain excluded from the tensor
catalog. This lets the two generic matchers share references without forcing
unsupported code into Linalg.

The provenance record establishes how MLIR was generated; it does not prove a
transliteration equivalent to its upstream library. The manual adaptations
listed below remain part of the trusted reference boundary. The current
validated executable ABI registry supports BLAS/LAPACK through OpenBLAS on CPU
and cuBLAS/cuSOLVER on CUDA. Other backends, including PVA, need imported
reference bodies and API bindings. An unsupported operation stays in the
application; it must not be counted as a library replacement.

## Transliteration rules

* Macros are instantiated: `FLOAT` = `double`, `BLASLONG` = `long`, `blasint` = `int`.
* Increments are specialised to 1 (`inc_x = inc_y = 1`), as lib_v2's `INC_CASE 1`.
* Column-major addressing `a[i + j*lda]` (or a column pointer bumped by `lda`)
  becomes `A[j][i]` of the C99 VLA parameter `double A[][lda]`: the same
  address. This is the only change to the code's shape; loop order, loop form
  (`while` loops and their counters) and arithmetic order are verbatim.
  Why not keep the flat code and let `--delinearize-memref-accesses` (in the
  production recipe) recover the 2-D view? The pass can: with the interface's
  check written as `__builtin_assume(lda >= MAX(1, m))` it proves `i < lda`
  (see `test/polygeist-opt/delinearize-memref-accesses.mlir`, `@gemv_assume`).
  But the spec pipeline does not yet accept a 2-D view of a flat parameter:
  debufferize, the `kernel.defn` extraction and the per-call array rank of
  the ABI all expect the parameter itself to be 2-D. The flat attempt is kept
  in `comparison-systems/delin/v3_flat_attempt/`.
* Interface logic that runs before the kernel (`if (beta != ONE) SCAL_K(...)`)
  and kernels called by kernels (`AXPYU_K` inside `ger`) are inlined.
* Scalar branches (`beta == 0`, `beta == 1`, `alpha == 0`) become separate
  specs or recorded assumptions, as in lib_v2. Argument checking and quick
  returns on sizes are dropped.
* Data-dependent zero-skip guards (`if (da == 0.0) return;` with
  `da = alpha*y[j]` in `ger`) are removed and listed under `deviations`.
* Only the column-major entry is transliterated; row-major CBLAS calls are
  the same kernels with operands swapped, which the matcher finds through
  operand and index permutations.

Spec names start with `openblas_` or `netlib_`. Lowering (`lower_v2.py`) uses
the validated ABI registry rather than either name prefix. It derives layouts
from strides and forwards proven bindings to external library calls. Generated
runtime adapters are written inside the build directory, leaving the checked-in
runtime templates untouched. Reference-body inlining tests validate import or
binding mechanics only; they do not establish vendor execution or performance.
